Kilian Valkhof — Stop using JavaScript for that

Gebruik niet automatisch JavaScript voor alles. Veel functionaliteiten kunnen tegenwoordig gewoon met HTML en CSS. Hij verwees naar de Rule of Least Power:

  1. eerst HTML
  2. dan CSS
  3. pas daarna JavaScript

JavaScript is krachtig, maar ook kwetsbaarder en zwaarder voor browsers.

Polypane

Tool van Kilian die helpt bij responsive design, gratis voor studenten. Ironisch genoeg is het gebouwd met JavaScript — dus hij is niet anti-JS.

React / JSX

Voor React developers: JSX is eigenlijk een dialect van HTML.

Custom switches

Veel developers bouwen switches met JavaScript (divs + onclick), maar dit kan gewoon met HTML/CSS:

  • checkbox input gebruiken
  • appearance: none verwijdert standaard styling
  • ::before voor custom styling
  • :checked voor actieve state
  • :focus voor toetsenbordgebruik

Gebruik niet zomaar outline: none zonder alternatief. Safari heeft zelfs een ingebouwde switch-stijl.

Smooth scrolling / page transitions

Vroeger vaak gedaan met jQuery. Nu kan het simpel met CSS: scroll-behavior: smooth. Gebruik ook prefers-reduced-motion voor mensen die gevoelig zijn voor animaties.

Accordions

Gebruik <details> om content te verbergen/tonen en <summary> als de altijd zichtbare klikbare titel. Voordelen: werkt zonder JavaScript, toegankelijker, met CSS aanpasbaar. Je kunt het pijltje aanpassen via ::marker.

Dialog

<dialog> kan modals vervangen. Nog soms een klein beetje JavaScript nodig, standaard verborgen, kan geanimeerd worden met @starting-style.

Field sizing

Maakt inputvelden automatisch even groot als hun content. Werkt momenteel in Google Chrome en Safari.

Select styling

Select-elementen waren vroeger lastig te stylen. Nieuwe mogelijkheden: ::picker(select) en appearance: base-select. Hiermee kun je dropdowns beter stylen zonder functionaliteit te verliezen. Werkt momenteel vooral in Google Chrome.

Scroll-driven animations

Animaties kunnen nu gekoppeld worden aan scrollgedrag via CSS in plaats van JavaScript.

Belangrijkste takeaway

Gebruik JavaScript alleen wanneer het echt nodig is. Moderne HTML en CSS kunnen veel meer dan developers vaak denken.

Peter Paul Koch — Alles over browsers

Browsers verbinden gebruikers met het web en moeten verschillende dingen kunnen verwerken:

  • HTML → structuur van een pagina
  • CSS → styling en layout
  • DOM → programmeerbare versie van HTML voor JavaScript
  • AOM → toegankelijkheid voor bijvoorbeeld screenreaders
  • Browser interface → tabs, zoekbalk etc.
  • JavaScript engine → voert JavaScript uit (apart van de rendering engine)

DOM

De DOM is HTML die door JavaScript aangepast kan worden. Als je JavaScript in de browser gebruikt, werk je meestal met de DOM. In Node.js gebruik je meestal geen DOM.

Parser

Een parser leest code (zoals HTML, CSS en JavaScript) en bepaalt wat alles betekent.

Layout

De layout engine bepaalt waar elementen staan en hoe groot ze zijn. Layout opnieuw berekenen kost veel performance en kan zorgen voor verspringende elementen ("popcorn layout").

Rendering engine

Verwerkt HTML en CSS, bouwt de DOM en AOM op en rendert de pagina. Eén rendering engine kan door meerdere browsers worden gebruikt, zoals Blink/Chromium bij:

  • Google Chrome
  • Microsoft Edge
  • Opera
  • Arc Browser

Core vs DOM

  • Core JavaScript = basis van de programmeertaal
  • DOM = manier waarop JavaScript HTML-elementen aanpast

Render blocking

CSS en JavaScript kunnen het laden van HTML tijdelijk stoppen. Bij scripts kun je dit verbeteren met:

  • normaal script → doe het nu
  • defer → doe het later
  • async → doe het wanneer het uitkomt

Gebruik meestal defer of async.

Backward compatibility

Browsers blijven oude code ondersteunen zodat oude websites blijven werken, zoals:

  • geen doctype
  • <body bgcolor="">
  • <frameset>

Browser als platform

Douglas Crockford noemde browsers: "The most hostile development platforms in the world" — omdat browsers rekening moeten houden met oude systemen, nieuwe technologie, verschillende apparaten en performance.

Browsergeschiedenis

  • 1990: eerste browser door Tim Berners-Lee
  • 1993: NCSA Mosaic → afbeeldingen
  • 1994: Netscape Navigator
  • 1995: Internet Explorer en Opera
  • 2003: Safari
  • 2004: Mozilla Firefox
  • 2008: Google Chrome
  • 2024: Ladybird

Kernpunt

Browsers lijken simpel, maar doen veel achter de schermen: code lezen, pagina's opbouwen, toegankelijkheid regelen en oude websites blijven ondersteunen.

Nils Binder — 9elements

Nils Binder is UX designer en frontend developer bij 9elements. Zijn talk ging over hoe je creativiteit kunt combineren met de meer gestructureerde werkwijze van bedrijven.

Design tools door de jaren heen

Vroeger werden websites vaak ontworpen in Adobe Photoshop, wat minder aansloot op hoe websites daadwerkelijk gebouwd werden. Nu wordt veel gewerkt met Figma, wat meer lijkt op hoe CSS werkt omdat het beter inspeelt op layouts en componenten.

Hij maakte ook een grap dat Tailwind + ChatGPT + Figma de "holy trinity of boredom" is, omdat veel websites daardoor op elkaar gaan lijken.

Denk in onderdelen, niet pixels

In plaats van obsessief naar pixels te kijken, moet je kijken naar grotere onderdelen en componenten van een design.

  • focus op structuur
  • focus op herbruikbare onderdelen
  • niet op perfecte pixel placement

CSS Grid & whitespace

Hij liet zien hoe je de fr unit in CSS Grid kunt gebruiken om witruimte beter te verdelen binnen layouts. Dit maakt layouts flexibeler.

Creatieve CSS voorbeelden

Hij liet een soort flipbook-effect zien dat gemaakt werd met afbeeldingen, CSS animations en de steps() function. Dit zorgde voor een frame-by-frame animatie effect.

Subgrid

Hij besprak ook subgrid: een grid binnen een ander grid waardoor child elementen dezelfde grid structuur kunnen volgen. Dit helpt bij consistente layouts.

Handige selectors

De CSS ::first-line selector kwam ook voorbij. Hiermee kun je alleen de eerste regel van tekst stylen.

View Transitions

Hij noemde ook de View Transitions API, waarmee je soepelere overgangen tussen verschillende pagina's kunt maken.

Websites/projecten

  • bonabry.de
  • 9elements / bonamic.de

Belangrijkste takeaway

CSS wordt steeds krachtiger waardoor je creatievere websites kunt maken zonder afhankelijk te zijn van zware design tools of JavaScript. Denk meer in systemen en componenten in plaats van losse pixels.

Robbert & Yolijn — Toegankelijke formulieren

Een formulier moet een duidelijke flow hebben:

  1. introductie/uitleg
  2. benodigde informatie invullen
  3. gebruiker laat gegevens controleren
  4. foutmeldingen tonen na verzenden
  5. duidelijke bevestiging na succesvolle verzending

Introductie

Maak vooraf duidelijk:

  • hoe lang het formulier duurt (bijv. 5 minuten)
  • hoeveel stappen er zijn (Stap 1 van 4)
  • of gebruikers nog documenten moeten opsturen

De tijdsinschatting moet realistisch zijn.

Validatie & feedback

Bij fouten: rode outlines, duidelijke foutmeldingstekst, samenvatting van fouten na verzenden. Bij succes: groene feedback, duidelijke bevestiging, uitleg over vervolgstappen.

Vraag alleen noodzakelijke informatie

  • geslacht is vaak niet nodig
  • vraag geen e-mailadres twee keer
  • gebruik geen onduidelijke afkortingen
  • leg uit waarom informatie nodig is

Labels & inputvelden

  • zet labels boven invoervelden
  • maak labels klikbaar door ze aan inputs te koppelen
  • houd labels kort en duidelijk
  • placeholders zijn geen vervanging voor labels
  • gebruik liever "verplicht/niet verplicht" dan alleen een *

Voorbeeld: Voornaam is beter dan voorna(a)m(en)

Design richtlijnen

  • duidelijke kleurcontrasten
  • klikbare elementen minimaal 44×44px
  • buttons aan het begin van een regel
  • voortgang altijd bovenaan tonen
  • consistente navigatie (volgende, vorige, annuleren)

Gebruiksgemak

  • automatisch invullen ondersteunen
  • copy/paste toestaan
  • browser autocomplete ondersteunen
  • voldoende witruimte houden voor autocomplete menu's
  • belangrijke uitleg zichtbaar houden

aria-describedby kan gebruikt worden voor extra uitleg.

Controle stap

Laat gebruikers altijd hun ingevulde gegevens controleren voordat ze definitief verzenden.

CSS sizing

Gebruik liever inline-size en block-size in plaats van width en height.

Flexibele validatie

  • geef maximale tekens duidelijk aan
  • voorkom onnodige restricties
  • accepteer meerdere invoerformaten

Bijvoorbeeld postcode met of zonder spatie.

Toetsenbord toegankelijkheid

Een formulier moet volledig zonder muis werken: tab, shift + tab, pijltjestoetsen. Daarnaast: logische tabvolgorde, duidelijke focus states en radio buttons bedienbaar met pijltjes.

Screenreaders & toegankelijkheid

Test formulieren met echte gebruikers. Screenreaders moeten kunnen voorlezen: labels, beschrijvingen, verplichte velden, foutmeldingen, formulierstappen en bevestiging na verzending. Feedback moet helpen, niet storend zijn.

Rosa — Hackers United

Rosa sprak over digitale onafhankelijkheid en duurzaamheid binnen technologie.

Planned obsolescence

Apparaten worden steeds moeilijker te repareren of gaan sneller "verouderd" aanvoelen. Dit zorgt ervoor dat mensen:

  • sneller nieuwe apparaten kopen
  • afhankelijker worden van grote techbedrijven
  • minder controle hebben over hun eigen apparaten

Ze koppelde dit aan de afhankelijkheid van vooral Amerikaanse Big Tech bedrijven.

Cloud en servers

De "cloud" is eigenlijk gewoon een plek waar websites en diensten gehost worden, vaak zonder dat gebruikers daar veel controle over hebben. Een server is in principe:

  • een computer
  • verbonden aan een router
  • die informatie opslaat
  • en verstuurt naar gebruikers

Duurzamere hosting

Node9 werd genoemd als voorbeeld van een meer eco-driven server/initiatief.

Static Site Generators

Static site generators kunnen duurzamer zijn omdat ze minder serverkracht nodig hebben.

  • minder belasting op servers
  • als alles faalt blijft markdown vaak nog leesbaar
  • overzichtelijke code

Voorbeeld: Eleventy (11ty)

Zelf hosten

Rosa moedigde aan om meer zelf te hosten, zoals Git repositories, messaging platforms en websites. Zo word je minder afhankelijk van grote platforms.

DIY / DIWO

DIY (Do It Yourself) en DIWO (Do It With Others) stonden centraal: zelf leren maken, maar ook samen kennis delen. Er werden ook community avonden genoemd zoals donderdagavond en vrijdag sociale avond.

Johann Huijkman — Toegankelijkheid & gebruikerservaring

"Je gaat het pas zien als je het doorhebt." En: "Je hoort het pas als je luistert."

De kern van de talk: toegankelijkheid begrijp je pas echt wanneer je luistert naar mensen die er dagelijks mee te maken hebben.

WCAG principes

De vier basisprincipes van WCAG:

  • Perceivable → content moet waarneembaar zijn
  • Operable → website moet bedienbaar zijn
  • Understandable → informatie moet begrijpelijk zijn
  • Robust → moet werken op verschillende technologieën/hulpmiddelen

WCAG is een handig hulpmiddel, maar niet de enige manier om een website toegankelijk te maken. Belangrijk: test ook met echte gebruikers.

Screenreaders & alt-tekst

Maak geen onnodige aanpassingen zonder kennis. Praat met mensen die al screenreaders gebruiken, want veel functies bestaan al. Niet elke afbeelding heeft uitgebreide alt-tekst nodig — als de afbeelding decoratief is mag deze leeg zijn (alt="").

Martijn — kan bijna niets zien

Problemen: knoppen zonder duidelijke hover/focus states, cookie banners waarbij scrollen niet werkt, slecht contrast, captcha's.

Wat helpt: korte en duidelijke tekst, schaalbare content, goed contrast, informatie logisch groeperen, duidelijke focus indicatoren.

Nauduah — beperkte mobiliteit

Problemen: felle kleuren, te veel informatie tegelijk, slechte concentratie door drukke interfaces, lang moeten zoeken naar informatie.

Wat helpt: duidelijke structuur, informatie gegroepeerd, visueel rustige websites, dark mode, gegevens kunnen opslaan.

Guido — autisme

Problemen: te veel visuele en audio prikkels, harde advertenties, te veel informatie, onduidelijke formuleringen.

Wat helpt: rustige layouts, voorspelbaarheid, duidelijke instructies, concrete tekst, weinig afleiding.

Toepassing op eigen project

Denk na waarom gebruikers met verschillende behoeften mogelijk afhaken bij jouw eigen project en hoe je dat kunt verbeteren.
